# 260902版 課内コメント対応レポート

## 1. このレポートの目的

本レポートは、課内から寄せられたコメントを受けて作成した `260902.html` について、コメントごとの要件解釈、実装内容、利用者への効果、技術上の判断と制約を整理したものです。

`260902.html` は、従来の年度・施設分類を中心としたアーカイブ型の見せ方から、利用者が「興味のあること」や「今いる場所・入力した住所」を起点にスポットを探せる発見型の地図へ改修した検討版です。既存の `index.html` は変更せず、比較や課内確認ができるよう別ファイルとして作成しています。

## 2. 対応対象となったコメント

対応対象は次の9点です。

1. ユーザーにとっては「何年に調査されたのか」は関係なさそう
2. 周辺地図とスポットの写真が並んで表示されるのは分かりやすい
3. スポットごとに検索用のタグ付けをしてもよいのではないか
4. 検索結果として該当するスポットがない場合は、その旨を表示したい
5. ユーザー自身の住所を入れると周辺のスポットが分かる機能がほしい
6. 区ごとの分類ができるとよい
7. カテゴリ（場所の性格）の分類を再考したい
8. 現在地に合わせた表示ができるとよい
9. 検索結果の反応・反映を分かりやすくしたい

## 3. 対応方針の概要

今回の改修では、調査を管理する側の情報より、地図を利用する人の探し方を優先しました。

- 年度切り替えを画面から取り除く
- 「施設」より広い意味を持つ「スポット」に呼称を変更する
- キーワード、区、カテゴリ、タグを組み合わせて絞り込めるようにする
- 住所または現在地を検索起点にし、近い順・距離範囲で探せるようにする
- 検索件数、適用中の条件、0件時の案内を常に見える形にする
- 地図、写真付き一覧、記事詳細、OSM情報、徒歩ルート案内という既存の長所を維持する

実装は従来どおりPure HTML + JavaScriptで完結させています。CSVはHTML内に埋め込まれているため、検索・分類・距離計算はブラウザ上で行われます。住所検索、背景地図、現在地取得、徒歩ルート検索には、それぞれ外部APIまたはブラウザ機能を利用します。

## 4. コメント別の対応内容

### 4.1 「何年に調査されたのか」は利用者には関係が薄い

#### 要件の解釈

年度は調査・更新を管理するうえでは重要ですが、一般利用者が行き先を探す際の第一条件にはなりにくいと判断しました。年度を前面に出すと、古い年度のスポットが現在利用できないように見えたり、検索操作を不必要に複雑にしたりする可能性もあります。

#### 実装内容

- 年度切り替えボタンを削除
- 一覧カードの年度表示を削除
- 詳細画面上部の年度表示を削除
- モバイルの絞り込み状態から年度を削除
- 絞り込みロジックから年度条件を削除

年度情報は元CSVに由来する調査記録として残りますが、`260902.html` の利用者向けUIには表示しません。これにより、データ管理上の来歴と、利用者向けの検索体験を分けています。

### 4.2 周辺地図とスポット写真の並列表示を維持する

#### 要件の解釈

地理的な位置と場所の雰囲気を同時に理解できる点は、既存ビューアの強みです。このため、新機能を追加しても地図中心の構成を崩さない方針としました。

#### 実装内容

- PCでは、左側にLeaflet地図、右側に写真付きスポット一覧を並べる構成を維持
- 一覧カードには、スポット写真、カテゴリ、区または距離、名称、タグ、住所を表示
- カード選択時は該当マーカーへ移動し、詳細画面で大きな写真と記事を表示
- スマートフォンでは地図と一覧を縦に並べ、地図の高さを画面高の約58%に調整

検索条件が変わると、地図上のマーカーと写真付き一覧が同時に更新されるため、両者の対応関係を保ったまま閲覧できます。

### 4.3 スポットごとの検索タグを追加する

#### 要件の解釈

一つの主カテゴリだけでは、「子どもと行ける」「本がある」「ワークショップがある」など、利用者の関心を十分に表せません。そのため、カテゴリとは別に複数付与できる検索タグを導入しました。

#### 実装内容

- 地図表示対象37件すべてに複数のタグを設定
- 検索画面には、利用頻度を想定した12個の主要タグを表示
  - 展示
  - カフェ
  - 飲食
  - 本
  - 買い物
  - 工芸
  - ワークショップ
  - 音楽
  - 子ども
  - 地域交流
  - 屋外
  - 福祉
- 一覧カードには先頭3件のタグを表示
- 詳細画面には、そのスポットに設定されたタグをすべて表示
- キーワード検索では、画面にボタン表示していない「イベント」「歴史」「子育て」などのタグも検索対象に含める

タグは `SPOT_META` にスポットID単位で定義しています。複数のタグボタンを選択した場合は、選択したタグのいずれかを持つスポットを表示するOR検索です。候補を過度に狭めず、関連する場所を広く発見できる挙動を採用しました。

#### 注意点

今回のタグは、記事タイトル、キャッチコピー、本文、施設の性格を基にした編集上の仮分類であり、公式分類ではありません。公開前には、タグ語彙、付与基準、表記統一、追加・削除の運用担当を決める必要があります。

### 4.4 該当スポットがない場合の表示を追加する

#### 要件の解釈

結果が0件になったときに一覧が空になるだけでは、検索中なのか、読み込みに失敗したのか、条件に一致しなかったのか判断できません。0件であることと、次に取れる操作を明示する必要があります。

#### 実装内容

検索結果が0件の場合、一覧領域に次の内容を表示します。

- 「該当するスポットはありません」という明確な見出し
- 現在の検索条件に一致する場所がなかったこと
- キーワードや絞り込み条件を変更する案内
- 「条件をすべて解除」ボタン

0件時にも画面上部の件数表示は `0` となり、条件表示と整合するようにしています。解除ボタンでは、キーワード、区、カテゴリ、タグ、距離範囲、住所検索の起点をまとめて初期化します。

### 4.5 入力した住所の周辺から探せるようにする

#### 要件の解釈

自宅、勤務先、駅、訪問予定地などを起点に、周辺の文化的な場所を探せる機能として実装しました。住所を施設データへ書き込むのではなく、検索時だけ一時的に使用する設計です。

#### 実装内容

1. 利用者が「住所から近くを探す」欄へ住所を入力
2. 国土地理院の住所検索APIへ検索語を送信
3. 最初の検索結果から緯度・経度と住所表記を取得
4. 検索地点を「起」マーカーとして地図に表示
5. 各スポットまでの直線距離をブラウザで計算
6. 初期状態では3km以内のスポットを近い順に表示
7. 距離範囲を「指定なし・1km・3km・5km」から変更可能にする

住所入力欄の下には、「住所は保存せず、検索時のみ国土地理院APIへ送信します」と表示しています。入力内容や検索地点はCSVへ保存せず、ページを閉じると失われます。

#### エラー時の案内

- 未入力の場合：「住所を入力してください」
- 該当住所がない場合：「住所を見つけられませんでした」
- APIへ接続できない場合：「住所検索に接続できませんでした」

検索中はボタンを無効化し、「検索中…」と表示して二重送信を防ぎます。

#### 注意点

- 複数候補を選択する画面は設けず、APIの最初の候補を採用しています
- 距離は徒歩ルート距離ではなく、Haversine式による概算の直線距離です
- 町名だけなど曖昧な住所では、利用者の意図と異なる地点になる可能性があります
- 国土地理院APIへの接続にはインターネット環境が必要です

### 4.6 区ごとの分類を追加する

#### 要件の解釈

さいたま市内で日常的に使われる地域単位として、10区による絞り込みを用意しました。市内のどのエリアにあるかを、地図操作だけに頼らず選べるようにするものです。

#### 実装内容

- 西区
- 北区
- 大宮区
- 見沼区
- 中央区
- 桜区
- 浦和区
- 南区
- 緑区
- 岩槻区
- 市外
- 区不明

各ボタンには該当件数を表示し、0件の区は選択できない状態にします。区は、国土地理院結果住所または参考住所に含まれる区名からブラウザ上で判定します。さいたま市外と判断できる住所は「市外」、判定できないものは「区不明」とします。

#### 注意点

区は独立したCSV列ではなく住所文字列から導出しているため、住所の表記方法が変わると判定結果が変わる可能性があります。継続運用では、公開用CSVに行政区コードまたは区名の正規化列を持たせる方法がより安定します。

### 4.7 カテゴリ（場所の性格）を再編する

#### 要件の解釈

従来のカテゴリには、活動内容と施設形態が同じ階層に混在していました。今回、地図の色分けに使う主カテゴリは「その場所がどのような種類の場所か」が伝わる施設形態寄りの分類へ整理し、活動内容はタグで補う構成に変更しました。

#### 新しい6カテゴリ

| カテゴリ | 主な対象 | 表示色 |
|---|---|---|
| ギャラリー・展示施設 | 展示や作品鑑賞を主目的とする場所 | 赤茶 |
| カフェ・飲食店 | 飲食を基盤に文化活動を行う場所 | 黄土 |
| 書店・ショップ | 本、雑貨、画材、作品等を扱う場所 | 青 |
| 工房・アトリエ | 制作、工芸、体験を中心とする場所 | 緑 |
| 文化施設・歴史・自然 | 美術館、資料的施設、農・自然環境等 | オリーブ |
| コミュニティスペース | 地域交流、子育て、居場所等を中心とする場所 | 紫 |

各スポットには主カテゴリを一つ設定し、地図マーカーの色と一覧・詳細画面のラベルに使用します。一つの場所が持つ複数の性格はタグで補完します。

#### 注意点

このカテゴリも公式分類ではありません。複合施設を一つのカテゴリへ割り当てる際には編集判断が入ります。今後は、分類定義と具体例をデータ更新手順に組み込み、担当者が変わっても判断が揃うようにする必要があります。

### 4.8 現在地に合わせた表示を追加する

#### 要件の解釈

従来の「現在地を取得」は、現在地マーカーを地図に示す機能でした。今回のコメントに合わせ、現在地を実際の検索条件として使い、近くのスポットを探せる機能へ拡張しました。

#### 実装内容

- ボタン表記を「現在地で探す」に変更
- ブラウザのGeolocation APIで現在地と精度を取得
- 現在地マーカーと精度範囲を地図に表示
- 現在地から3km以内を初期条件に設定
- 各スポットまでの直線距離を計算し、近い順に並べ替え
- 一覧カードに現在地からの距離を表示
- 地図の表示範囲へ現在地と検索結果を含める
- 取得後は「現在地で再検索」と表示し、位置を更新できるようにする

施設詳細の冒頭にある徒歩ルート案内は維持しています。周辺検索では軽量な直線距離を使い、実際に訪問するスポットを選んだ後はLeaflet Routing Machineと徒歩用OSRMによるルート案内を利用する、二段階の設計です。

#### 注意点

- 現在地取得には利用者の許可が必要です
- `file://` ではブラウザによって位置情報が利用できないため、HTTPSまたはlocalhostでの確認が必要な場合があります
- 精度は端末、屋内外、通信環境によって変化します
- 取得した現在地はCSVへ保存しません

### 4.9 検索結果の反応・反映を分かりやすくする

#### 要件の解釈

操作後に何が変わったかを、地図を見比べなくても理解できる必要があります。そのため、件数だけでなく、現在適用されている条件と0件状態を言葉で返すようにしました。

#### 実装内容

- 入力やフィルタ選択のたびに即時更新
- 「37件・すべてのスポット」のように結果件数を一覧上部へ表示
- 条件適用時は「浦和区 / カフェ・飲食店 / カフェ」のように条件を併記
- 住所・現在地検索時は「○○から3km以内」のように検索起点と範囲を表示
- 検索結果更新時に、結果概要の文字色を短時間変化させる
- 一覧と地図マーカーを同時に更新
- 絞り込み中だけ「条件をすべて解除」ボタンを表示
- モバイルの絞り込みボタンにも選択中の区・カテゴリ・タグを表示
- 0件時は専用メッセージと解除操作を表示

これにより、「操作を受け付けたか」「何件になったか」「どの条件が効いているか」「0件の理由は何か」を一続きで確認できます。

## 5. 検索条件の組み合わせ方

検索条件は次の順序で同時に適用されます。

1. 区が選ばれている場合、その区だけを残す
2. カテゴリが選ばれている場合、そのカテゴリだけを残す
3. タグが選ばれている場合、選択タグのいずれかを持つスポットを残す
4. 住所または現在地と距離範囲が設定されている場合、範囲内だけを残す
5. キーワードがある場合、名称、キャッチコピー、住所、区、カテゴリ、タグ、記事本文、OSM名称を横断検索する
6. 住所または現在地が設定されている場合は距離順、それ以外はスポットID順に並べる

条件同士はANDで組み合わせ、複数タグの内部だけはORで評価します。例えば「浦和区」「カフェ・飲食店」「展示または音楽」を同時に指定できます。

## 6. スマートフォン表示の整理

追加した検索項目が地図を圧迫しないよう、760px以下では次の順序に整理しています。

1. キーワード検索
2. 住所検索
3. 座標確認・現在地検索
4. 絞り込み開閉ボタン・件数
5. 地図
6. 写真付きスポット一覧

区、カテゴリ、タグ、距離範囲は通常時には折りたたみ、必要なときだけ「絞り込み」から展開します。選択肢は横スクロールできるボタン列とし、画面を縦方向に占有しすぎないようにしました。

また、キーワード検索欄と住所検索欄は、PC表示で上端が揃うよう `.controls` の配置を `align-items: start` に変更しています。

## 7. データとプライバシーの扱い

### ブラウザ内で扱う情報

- CSVから読み込んだスポット情報
- 選択中の区、カテゴリ、タグ、距離範囲
- 住所検索APIから返された検索地点
- Geolocation APIから得た現在地と精度
- 各スポットまでの直線距離

住所入力と現在地は、ページ内の検索と表示にのみ使用し、CSVやリポジトリへ書き込みません。

### 外部へ通信する情報

| 機能 | 送信先 | 主な送信内容 |
|---|---|---|
| 住所検索 | 国土地理院 住所検索API | 利用者が入力した住所文字列 |
| 背景地図 | OpenStreetMapタイルサーバー | 表示範囲に対応するタイル要求 |
| 徒歩ルート | FOSSGISの徒歩用OSRM | 現在地と選択スポットの座標 |

ブラウザのGeolocation API自体の位置取得方法や権限管理は、利用端末とブラウザの仕様に依存します。

## 8. 実装上の主な判断

### 年度は削除ではなく、利用者向けUIから分離

調査年度はデータの来歴や更新管理に必要なため、元データから消去するのではなく、検索・表示の主軸から外しました。

### カテゴリとタグの役割を分離

カテゴリは地図上で一目で分かる一つの主分類、タグは複数の関心や活動を表す補助分類としました。色分けが複雑になりすぎることを防ぎながら、検索語彙を増やしています。

### 周辺候補の探索は直線距離、訪問時は徒歩ルート

全スポットに対して外部ルートAPIを呼ぶと、表示が遅くなりサービスへの負荷も高くなります。候補検索はブラウザ内の直線距離計算で即時に行い、個別スポットの詳細でのみ徒歩ルートを検索します。

### 検索状態をURLやローカルストレージへ保存しない

今回の検討版では、住所や現在地を含む検索状態を永続化していません。再読み込みで初期状態へ戻る単純な構成とし、個人に関わる検索起点を意図せず残さないようにしています。

## 10. 課内確認時の推奨チェック項目

### PC表示

- キーワード検索と住所検索の上端が揃っているか
- 地図と写真付き一覧を同時に把握できるか
- 区・カテゴリ・タグの意味が直感的か
- 検索後の件数と条件表示に気づけるか
- 0件表示から条件解除へ迷わず進めるか

### スマートフォン表示

- 地図より上の操作項目が多すぎないか
- 絞り込みを閉じた状態でも、選択中の条件が分かるか
- 横スクロールする区・カテゴリ・タグを操作しやすいか
- 地図と一覧の移動量が許容範囲か

### 位置情報機能

- 現在地の許可、拒否、タイムアウト時の表示が理解できるか
- 住所検索結果の地点が入力意図と合っているか
- 1km、3km、5km、指定なしの違いが分かるか
- 直線距離と徒歩ルート距離を混同しないか

## 11. 今後の改善候補

今回の対応でコメントに必要な基本機能は実装しましたが、公開・継続運用に向けては次の改善が考えられます。

1. タグとカテゴリの編集基準を文書化し、担当者間の判断を統一する
2. 区名または行政区コードを公開用CSVの独立列として管理する
3. 住所検索で複数候補を表示し、利用者が地点を選べるようにする
4. タグの選択方式がOR検索であることを画面上でも説明する
5. URLクエリへ個人情報を含めずに、区・カテゴリ・タグだけを共有できるようにする
6. キーボード操作、スクリーンリーダー、色覚多様性を含むアクセシビリティ試験を行う
7. 実機スマートフォンと複数ブラウザで、位置情報許可やレイアウトを確認する
8. 分析を行う場合も、住所や正確な現在地を収集しない計測方針を定める
9. 施設の営業状況や記事情報を継続的に更新する運用を決める
